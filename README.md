# Sierksma's conjecture for nine points in R³: Lean 4 formalization

Version 1.0.0.

This repository contains a machine-checked proof, in Lean 4 with Mathlib, of the main theorem
(Theorem 1.2) of the paper *Sierksma's conjecture for nine points in R³* by Sungsoo Na:
any 9 points in ℝ³ have at least 8 Tverberg partitions into 3 parts.

## The theorem

`Challenge.lean` states the theorem with Mathlib definitions only:

```lean
theorem sierksma_three_three (p : Fin 9 → EuclideanSpace ℝ (Fin 3)) :
    8 ≤ Nat.card {Q : Finpartition (Finset.univ : Finset (Fin 9)) //
      Q.parts.card = 3 ∧
        (⋂ A ∈ Q.parts, convexHull ℝ (p '' (A : Set (Fin 9)))).Nonempty} := by
  sorry
```

In words: for every labelled 9-tuple of points `p 0, …, p 8` in ℝ³ (points may coincide), at least 8
partitions of the index set `{0, …, 8}` into three nonempty blocks have convex hulls with a common point.
A `Finpartition` is a set of blocks, so partitions are counted without an order on the blocks.
This is Sierksma's bound ((r−1)!)^d for d = 3, r = 3.

`Solution.lean` states the same declaration and proves it.

## What is checked, and what is not

If `lake build` succeeds, then:

- `sierksma_three_three` in `Solution.lean` is a complete proof of the declaration in `Challenge.lean`,
  checked by the Lean kernel.
- `Audit.lean`, part of the default build, makes the build fail unless the three head theorems
  (`sierksma_three_three`, `SierksmaLean.sierksma_three_three`, `SierksmaLean.main_theorem`) depend on no
  axioms other than `propext`, `Classical.choice` and `Quot.sound`, and unless no declaration of the
  `SierksmaLean` library uses `sorry` directly. The only `sorry` in the repository is the one in
  `Challenge.lean`: that file is the statement to compare against, not part of the proof.
- The large finite case analyses are certificates checked by the kernel itself (`decide +kernel`).
  The project contains no `native_decide`, `bv_decide`, `implemented_by`, `extern`, `unsafe` code and no
  `axiom` declaration, so no compiled code is trusted.

What you still trust or check yourself:

- that the statement above says what you expect. It is the only part you need to read: the internal
  vocabulary of `SierksmaLean/` is connected to it by a proved equivalence (`Sierksma.public_iff`);
- the Lean kernel, the toolchain `v4.33.1`, and the Mathlib definitions used in the statement
  (`EuclideanSpace`, `convexHull`, `Finpartition`, `Nat.card`);
- the precompiled Mathlib files, if you fetch them with `lake exe cache get` as below. Lean does not
  re-check compiled files that it imports, so a rebuild with the cache also trusts these downloaded
  files. Building Mathlib from its sources instead (run `lake build` without `lake exe cache get`)
  avoids this, at the cost of many more CPU-hours.

The certificates were generated by programs outside this repository. They are not part of the trusted
base: the kernel checks every certificate.

**Relation to the paper.** The formal proof follows the plan of the paper: a covering property for the
Tverberg partitions of a generic configuration, a finite step, and a limit argument that passes to
arbitrary 9-tuples; it also uses the paper's classification lemma (Lemma 3.4, `Sierksma.classification`).
It differs from the paper in three places, described in Section 7 of the paper, and uses neither Dold's
theorem nor Hell's parity theorem:

- (a) topology: instead of Dold's theorem, a signed count of zeros, by a degree argument for equivariant
  maps that are affine on simplices (`Sierksma.pl_dold_signed_count`), for configurations in an explicit
  open dense set (`Sierksma.signed_twist_identities`, `Sierksma.generic_signed`);
- (b) parity: instead of Hell's parity theorem, the identities (I1) and (I2) of Section 7, which exclude
  every covering family of at most seven admissible partitions (partitions into three blocks of at most
  4 points each);
- (c) finite step: instead of the paper's classification of matching covers (Theorem 5.5), a direct search
  over the families of at most seven admissible partitions that cover all 76,545 twisted constraints,
  recorded as certificates and checked in the kernel (`Sierksma.FB.*`).

The formal proof certifies Theorem 1.2. The intermediate results of the paper, the covering numbers
β_A = 7 and β′_A = 8 and Theorem 5.5, are not formally verified: they rest on the proofs and computations
of Sections 3 to 5 of the paper.

## How the proof is organised

`SierksmaLean.main_theorem` (in `SierksmaLean/Main.lean`) is `Sierksma.main`, which combines four results:

- `Sierksma.generic_signed`: on a dense set of configurations, a signed system of Tverberg partitions
  exists whose support is exactly the set of Tverberg partitions;
- `Sierksma.finite_signed`: every signed system supported on partitions whose blocks have at most 4
  points has support of size at least 8 (a finite statement, proved with kernel-checked certificates in
  `Sierksma.FB.*`);
- `Sierksma.classification`: for configurations in strong general position, every block of a Tverberg
  partition has at most 4 points;
- `Sierksma.count_lower_of_dense`: a lower bound on a dense set of configurations holds everywhere.

`Sierksma.public_iff` then transfers the bound to the Mathlib statement of `Challenge.lean`.

## Rebuilding

Requirements, measured with a clean build of this repository on a 64-core 64-bit Arm (aarch64) Linux machine
with 495 GiB of memory (the record is in `receipts/`):

| | |
|---|---|
| `lake exe cache get` | 42 seconds (downloads prebuilt Mathlib) |
| `lake build` | 39 minutes wall clock with 64 parallel jobs, 14.5 CPU-hours |
| memory | up to 13.3 GiB for a single Lean process; about 72 GiB in use in total with 64 parallel jobs |
| disk | about 33 GB (`.lake` 30 GB including Mathlib, toolchain 3 GB) |

With less memory, limit the number of parallel jobs, e.g. `LEAN_NUM_THREADS=8 lake build`.
Estimated wall clock from the measured module times: 8 jobs about 2 hours, 16 jobs about 1 hour;
never below about 30 minutes (the longest chain of dependent modules).

Steps (Linux or macOS, with `git` and `curl`):

```sh
curl -sSfL https://raw.githubusercontent.com/leanprover/elan/master/elan-init.sh | sh -s -- -y --default-toolchain none
export PATH="$HOME/.elan/bin:$PATH"
cd <repository root>
lake exe cache get
lake build
lake env lean Check.lean
```

Do not run `lake update`: `lake-manifest.json` pins every dependency.

Expected output. `lake build` prints exactly one warning about `sorry`, for the challenge statement,

```
warning: Challenge.lean:10:8: declaration uses `sorry`
```

(the other warnings are linter style notes) and ends with

## Independent check with Comparator

`config.json` configures [Comparator](https://github.com/leanprover/comparator). It rebuilds `Challenge`
and `Solution` in a sandbox, exports both environments, checks that `sierksma_three_three` has the same
statement in both and uses only the three permitted axioms, and replays the whole solution environment
in the Lean kernel. Comparator and its exporter `lean4export` must be built with the Lean version of this
project (v4.33.1); see the Comparator README for the sandbox it needs. The replay is single-threaded and
re-checks every certificate, so a run takes hours.

A Comparator run on these Lean sources passed. Comparator `v4.33.0` (commit
`3927ad383f208ae977c340a91c48ac9b497d2097`) and lean4export `v4.33.0` (commit
`15f6055e299ad5b89345e533cc2192f4cc00f659`), both built with Lean v4.33.1, ran with the landrun sandbox
(commit `811cfff51ceaf3d9843708aa6d22e9b84ccac8b4`) as an unprivileged user, with Unix-domain sockets
blocked for the whole run as the Comparator README recommends, on the tree of the clean build recorded in
`receipts/` (its sandboxed builds of `Challenge` and `Solution` found that tree up to date). The run ended with

```
Lean default kernel accepts the solution
Your solution is okay!
```

and exit status 0, after 5 hours 2 minutes on one core, with at most 12.8 GiB of resident memory.
Before printing this, Comparator checked that `sierksma_three_three` has the same statement in
`Challenge` and `Solution`, and that every constant used in that statement, together with the constants
those depend on, definitions included, is identical in the two environments; that the proof uses no
axioms other than `propext`, `Quot.sound` and `Classical.choice`; and it replayed the exported solution,
which is the theorem together with everything it depends on, the Mathlib and core declarations
included, into the Lean kernel, starting from an empty environment. Both environments were built from
the same precompiled Mathlib files, so the run does not check that the Mathlib definitions in those
files agree with the Mathlib sources.

## Repository layout

| path | contents |
|---|---|
| `Challenge.lean` | the theorem statement (Mathlib only), with `sorry` |
| `Solution.lean` | the same declaration, proved from `SierksmaLean.sierksma_three_three` |
| `Audit.lean` | build-time check of axioms and `sorry` (see above) |
| `Check.lean` | `#check` and `#print axioms` for readers; not built by default |
| `config.json` | Comparator configuration |
| `SierksmaLean/Statement.lean` | `MainStatement` (project vocabulary) and `PublicStatement` (Mathlib vocabulary) |
| `SierksmaLean/Main.lean` | the head theorems `SierksmaLean.main_theorem` and `SierksmaLean.sierksma_three_three` |
| `SierksmaLean/Definitions/` | 25 definition modules `Def_<name>.lean` |
| `SierksmaLean/Theorems/` | 1,826 modules `Thm_<name>.lean`, one per lemma: its statement, proved by `Proof_<name>` |
| `SierksmaLean/Proofs/` | 1,826 modules `Proof_<name>.lean`; a proof uses other lemmas only through `Theorems/` |
| `lakefile.toml`, `lean-toolchain`, `lake-manifest.json` | build configuration and version pins |
| `receipts/` | records of a clean build and of a Comparator run of these Lean sources |

In a module name, `_` stands for the dots of the Lean name: `Thm_Sierksma_FB_cAS_44` states
`Sierksma.FB.cAS_44`. The lemmas fall into `PLDegree.*` (8), `Sierksma.*` (1,033) and `Sierksma.FB.*`
(785, the finite block). The default build has 3,683 modules.

## Receipts

`receipts/` holds the unedited output of the clean build of these Lean sources: `receipts/build.log`
(`lake build`), `receipts/build.time` (GNU `time -v` of `lake build`) and `receipts/check.out`
(`lake env lean Check.lean`). `receipts/build_summary.txt` is derived from `receipts/build.log` (the
numbers of built modules, errors and `sorry` warnings, and the axiom-check lines), and
`receipts/machine.txt` gives the architecture, cores and memory of the machines, the Lean, Lake and
Mathlib versions, and the Comparator tool versions. `receipts/comparator.log` is the output of the
Comparator run, each line prefixed with the UTC time at which it was written to the log, and
`receipts/comparator.time` is GNU `time -v` of the Comparator command.
